## Part A — Night & Sleep (ข้อ 6a + 18)

**ทำไมมาก่อน:** ไม่แตะ database, ไม่แตะ API contract, อยู่ในฝั่ง client ล้วน
และมันคือเรื่องที่เจ้าของเล่าเองว่าเจ็บจริง — หลับคาหนังแล้วตื่นมาหนังยังเล่นอยู่

### A1 — Sleep Mode

ผู้ใช้ตั้งว่า "ฉันจะนอนใน 30 นาที" (ตัวเลือก: 15 / 30 / 60 / จบตอนนี้)

พฤติกรรมเมื่อถึงเวลา ต้องนุ่ม ไม่ใช่ตัดจบ:

1. เหลือ 60 วิ → ขึ้นการ์ดเงียบ ๆ "จะหยุดใน 1 นาที · แตะเพื่อดูต่อ"
2. เหลือ 20 วิ → ค่อย ๆ ลดเสียงลงจนเป็นศูนย์
3. ถึงเวลา → `pause()` + หรี่จอ + บันทึก progress ทันที

**การตัดสินใจทางเทคนิคที่สำคัญ:** เก็บ *เวลาเป้าหมายเป็น wall-clock*
(`sleepDeadline: number` เป็น epoch ms ใน `localStorage`) ไม่ใช่ `setTimeout`
เปล่า ๆ เพราะบนมือถือ timer ถูกแช่ตอนแอปพับหลังบ้าน — ผู้ใช้กลับมาแล้วต้องเจอ
สถานะที่ถูกต้อง ไม่ใช่ timer ที่เพี้ยนไปครึ่งชั่วโมง

`"จบตอนนี้"` เป็นตัวเลือกที่ต่างออกไป: ไม่ใช้ deadline แต่ผูกกับจุดจบของ episode
ปัจจุบัน แล้วปิด autoplay ตอนถัดไป — ตรงกับพฤติกรรมจริงของคนดูซีรีส์ก่อนนอน

### A2 — Night Mode (Cinema Mode)

กดครั้งเดียว เปลี่ยนพร้อมกัน:

- ลดความสว่างของ UI chrome (ไม่ใช่ตัววิดีโอ — ห้ามเอา `filter: brightness()`
  ไปทับ `<video>` เด็ดขาด มันฆ่าสีของหนัง)
- subtitle เปลี่ยนไปใช้ token ที่คอนทราสต์ต่ำลง ไม่ใช่ขาวจ้า
- ปิด autoplay ตอนถัดไป
- ปิดเสียง/haptic ของ UI

**วิธี implement:** `data-night="on"` บน `<html>` แล้ว override CSS custom
properties ใน `globals.css` — ไม่ใช่ prop ที่ต้องส่งลงไปทุก component
ระบบ design token ที่มีอยู่แล้วรองรับวิธีนี้อยู่แล้ว

**การเสนอแบบไม่กวน:** ถ้าเวลาเครื่อง 22:00–05:00 และยังไม่เคยเปิด ให้เสนอ
**ครั้งเดียวตลอดกาล** ถ้าปัดทิ้งคือปัดทิ้งถาวร ห้ามถามซ้ำทุกคืน

### สิ่งที่ต้องระวัง

- ทั้งสองโหมดต้องเคารพ `prefers-reduced-motion` (fade → ตัดทันที)
- Sleep timer ต้อง `PUT /me/watch-history/:episodeId` ก่อนหรี่จอเสมอ
  ไม่งั้นผู้ใช้ที่หลับไปจะเสีย progress — ซึ่งคือ bug ที่ฟีเจอร์นี้ตั้งใจมาแก้พอดี

## Part B — Time-aware (ข้อ 1 + 8 + 19)

ก้อนใหญ่สุด และเป็นฐานรากของอีกสองข้อ ทำครั้งเดียวได้สามฟีเจอร์

### B0 — ฐานราก: `SceneMarker`

```prisma
enum SceneMarkerKind {
  INTRO
  RECAP
  CREDITS
}

model SceneMarker {
  id           String          @id @default(uuid())
  episodeId    String
  kind         SceneMarkerKind
  startSeconds Int
  endSeconds   Int

  episode Episode @relation(fields: [episodeId], references: [id], onDelete: Cascade)

  @@unique([episodeId, kind])
  @@index([episodeId])
  @@map("scene_markers")
}
```

`@@unique([episodeId, kind])` — หนึ่ง intro ต่อหนึ่งตอน จงใจให้แคบไว้ก่อน
ถ้าเจอเคสที่มี recap สองช่วงค่อยกลับมาคลาย constraint

**marker ไม่ใช่ความลับ** — ต่างจาก `videoUrl` ที่ถูกถอดออกใน
`movies.service.ts` (`toDto`) เพราะมันคือสิ่งที่ทำให้ดูหนังได้จริง
marker เป็นแค่ metadata เรื่องเวลา ส่งไปกับ episode payload ได้ตรง ๆ
แต่ยังต้องไหลผ่าน `toDto()` เหมือนทุกอย่าง เพื่อไม่ให้มี path ที่เลี่ยงการ strip

**ใครใส่ marker:** เฟสแรกใส่มือผ่าน seed/admin ห้ามหลอกตัวเองว่าจะมี
auto-detection ตั้งแต่วันแรก ฟีเจอร์ต้องทำงานถูกต้องเมื่อ marker เป็นค่าว่าง
(ไม่มี marker = ไม่มีปุ่มข้าม = ETA ไม่หักเวลา) นี่คือ degradation ที่ต้องเทสต์

### B1 — "ดูจบกี่โมง?" (ข้อ 19)

ตรรกะทั้งหมดอยู่ใน pure function เดียว เทสต์ได้โดยไม่ต้องมี DOM:

```ts
// apps/flick-app/src/features/playback/finishTime.ts
export function estimateFinishTime(input: {
  now: Date;
  remainingSeconds: number;   // จาก durationMinutes − progressSeconds
  skippableSeconds: number;   // ผลรวมจาก SceneMarker
  autoSkip: boolean;
  playbackRate: number;
}): { finishesAt: Date; savedSeconds: number };
```

แสดงผลสองที่:
- **หน้ารายละเอียดหนัง** ก่อนกดเล่น: "1 ชม 47 นาที · เริ่มตอนนี้จบ 22:07"
- **ในเพลเยอร์** ตอนเรียก overlay: "จบ 22:07" และถ้าเปิด auto-skip
  ให้บอกส่วนต่าง "ข้าม intro/credits แล้วเร็วขึ้น 4 นาที"

จุดที่ต้องคิดให้จบ: ผู้ใช้ pause แล้วเดินไปเข้าห้องน้ำ 10 นาที ETA ต้องขยับ
→ คำนวณใหม่จาก `now` ทุกครั้งที่ overlay เปิด **ห้าม** ตรึงค่าไว้ตอนกดเล่น

### B2 — "ข้ามสิ่งที่ไม่อยากดู" (ข้อ 8)

ปุ่มข้ามโผล่เมื่อ `currentTime` ตกอยู่ในช่วง marker แล้วหายไปเองเมื่อพ้นช่วง
มีสวิตช์ "ข้ามอัตโนมัติ" ใน settings (ค่าเริ่มต้น: ปิด — การกระโดดเองโดยไม่ขอ
เป็นพฤติกรรมที่น่าตกใจในครั้งแรกที่เจอ)

**ตัดออกจากเฟสนี้:** "ข้ามฉากที่บันทึกไว้ว่าเคยดู" ในภาพข้อ 8
ต้องเก็บ watch coverage เป็นช่วง ๆ ต่อผู้ใช้ (ไม่ใช่แค่ `progressSeconds`
ค่าเดียวอย่างที่ `WatchHistory` เก็บอยู่) เป็นระบบคนละขนาดกัน
ทางแทนที่ถูกกว่าและได้ผลเกือบเท่ากัน: ตอนดูซ้ำ ให้เสนอ "ดูต่อจากนาทีที่ 43"
ซึ่ง `progressSeconds` ที่มีอยู่รองรับได้เลย

### B3 — ตัวกรอง "มีเวลาเท่านี้" (ข้อ 1)

**คำถามออกแบบที่สำคัญที่สุดใน Part นี้:** กรองที่ระดับ *เรื่อง* หรือ *ตอน*

ในระบบนี้ทุกอย่างเป็น Movie → Season → Episode แม้แต่หนังเดี่ยว (ดู `seed.ts`)
ถ้ากรองที่ระดับเรื่อง ซีรีส์ 12 ตอนจะไม่มีวันโผล่ในตัวกรอง "30 นาที"
ทั้งที่ตอนถัดไปยาว 24 นาทีและผู้ใช้ค้างอยู่พอดี — ซึ่งเป็นคำตอบที่แย่มาก

**ข้อเสนอ: กรองที่ระดับตอน** ผลลัพธ์คือ "สิ่งที่กดเล่นได้เลยตอนนี้"

```ts
// GET /movies/fits?maxMinutes=30&mood=cozy
interface FitsResponse {
  items: Array<{
    movie: Movie;
    episode: Episode;
    kind: 'film' | 'next_episode' | 'first_episode';
    runtimeMinutes: number;      // หักเวลาที่ข้ามได้แล้ว
    finishesAtHint: string;      // ISO — ให้ client แสดง "จบ 22:07"
  }>;
}
```

`/movies` ปัจจุบันเป็น `@Public()` และแคชไว้ที่ key `movies:all` 5 นาที
(`movies.service.ts`) โดยจะ bypass แคชเมื่อมี `q` — endpoint ใหม่นี้เดินตาม
แพตเทิร์นเดิม: มีพารามิเตอร์กรอง = ไม่แตะแคช และเนื่องจาก `kind: 'next_episode'`
เป็นข้อมูลรายบุคคล endpoint นี้จึง **ห้ามเป็น `@Public()`** — ต้องแยกจาก
`/movies` ที่แคชร่วมกันทุกคน

UI คือ sheet แบบเลือกตั๋วเครื่องบินตามที่เจ้าของว่าไว้: แถวเวลา (15/30/60/90)
บวกแถวอารมณ์จาก Part C ปุ่มเดียวจบ ไม่มีฟอร์ม

## Part C — Discovery (ข้อ 2 + 4 + 6b)

### C1 — Mood Match (ข้อ 2)

เดินตามโครง `Genre`/`MovieGenre` ที่มีอยู่แล้วเป๊ะ ๆ:

```prisma
model Mood {
  id    String @id @default(uuid())
  slug  String @unique
  name  String
  emoji String

  movies MovieMood[]
  @@map("moods")
}

model MovieMood {
  movieId String
  moodId  String

  movie Movie @relation(fields: [movieId], references: [id], onDelete: Cascade)
  mood  Mood  @relation(fields: [moodId], references: [id], onDelete: Cascade)

  @@id([movieId, moodId])
  @@map("movie_moods")
}
```

หกอารมณ์ตั้งต้นตามภาพ: เหงา / เครียด / อยากหัวเราะ / อยากร้องไห้ / อยากลุ้น /
อยากได้แรงบันดาลใจ

**mood ≠ genre** และนี่คือจุดที่ฟีเจอร์นี้จะพังถ้าทำมักง่าย: หนังดราม่าเรื่องหนึ่ง
อาจตอบโจทย์ทั้ง "อยากร้องไห้" และ "อยากได้แรงบันดาลใจ" ขณะที่อีกเรื่องในแนวเดียวกัน
ไม่ตอบโจทย์ทั้งคู่ **ห้าม derive mood จาก genre โดยอัตโนมัติ** ต้องติดแท็กมือ
(ครั้งแรกทำที่ `seed.ts` ต่อไปทำผ่านหน้า admin) ถ้าไม่มีคนติดแท็กจริง ฟีเจอร์นี้
ไม่ควรขึ้น production

### C2 — กดค้างที่โปสเตอร์ดูพรีวิว (ข้อ 4)

`Movie.trailerUrl` มีอยู่แล้ว และ `public/videos/*-preview.m4v` ก็มี

ข้อกำหนดที่ห้ามพลาด:
- **ห้ามผ่าน `/playback/:id/authorize`** — พรีวิวคือของการตลาด ไม่ใช่คอนเทนต์
  ที่ต้องมี entitlement ถ้าเอาไปผูกกับ authorize จะกลายเป็นการเปิดช่องให้
  คนที่ไม่ได้สมัครดึง URL วิดีโอจริง
- กดค้าง 400 ms และ **ยกเลิกทันทีถ้านิ้วเลื่อนเกิน 10 px** — ไม่งั้นจะแย่งการ
  scroll ในหน้า shelf ซึ่งเป็นท่าหลักของแอป
- muted + `playsInline` เสมอ, หยุดเองที่ 10 วินาที
- เคารพ `prefers-reduced-motion` และ `navigator.connection.saveData` → แสดงภาพนิ่ง
- desktop: ใช้ hover intent ไม่ใช่ long-press

### C3 — "ฉันเคยดูเรื่องนี้หรือยัง?" (ข้อ 6b)

```ts
// GET /me/watch-status?movieIds=a,b,c   (ต้อง auth)
type WatchStatus = Record<string, {
  state: 'none' | 'partial' | 'watched';
  percent: number;              // 0–100 → ป้าย "ดูถึง 68%"
  lastWatchedAt: string | null; // → "ดูเมื่อ 3 เดือนก่อน"
}>;
```

**เหตุผลที่ต้องแยก endpoint ไม่ยัดลงใน `/movies`:** `/movies` เป็น `@Public()`
และแคชผลลัพธ์เดียวร่วมกันทุกคนที่ key `movies:all` การเอาสถานะรายบุคคลไปใส่
คือการทำให้ประวัติการดูของคนหนึ่งรั่วไปหาอีกคนผ่านแคช — เป็นบั๊กความเป็นส่วนตัว
ไม่ใช่แค่บั๊กความถูกต้อง client เรียกสองทางแล้ว merge เอง

`percent` คำนวณจาก `progressSeconds / (durationMinutes × 60)` รวมทุกตอน
ถ้า `completed = true` ให้ถือเป็น 100 เสมอ ไม่ต้องเชื่อ `progressSeconds`
(ผู้ใช้กด skip credits แล้วปิดแอปจะได้ 94% ทั้งที่ดูจบแล้ว)

## Part D — Flicer Passport (💎)

`GET /me/passport` — endpoint อ่านอย่างเดียว รวมยอดจากตารางที่มีอยู่

**เฟส 1 ทำได้ทันทีจากข้อมูลที่มี:** จำนวนเรื่องที่ดูจบ, ชั่วโมงสะสม,
แนวที่ดูมากที่สุด (จาก `MovieGenre` + `WatchHistory`), จำนวน like

**เฟส 2 ต้องมีของใหม่ก่อน:**
- "ดูหนังเกาหลี 38 เรื่อง" → ต้องมี `Movie.originCountry`
- "ให้คะแนนเฉลี่ย 8.1" → ต้องมีระบบให้คะแนน ซึ่ง `Interaction` (LIKE/DISLIKE)
  รองรับไม่ได้ เป็นฟีเจอร์แยกที่ต้อง brainstorm ของตัวเอง

**ทำท้ายสุดเพราะเหตุผลที่ไม่ใช่เรื่องเทคนิค:** Passport ที่ขึ้นว่า
"ดูแล้ว 3 เรื่อง · 2 ชั่วโมง" ดูน่าสมเพชกว่าไม่มี ฟีเจอร์นี้ต้องรอให้ผู้ใช้จริง
สะสมประวัติก่อน ไม่ใช่รอโค้ด

## ลำดับที่แนะนำ

| ลำดับ | Part | แตะ schema | เหตุผล |
|---|---|---|---|
| 1 | **A — Night & Sleep** | ไม่ | ไม่มี dependency, แก้เรื่องที่เจ้าของเจ็บจริง, พิสูจน์ทิศทางได้เร็ว |
| 2 | **B — Time-aware** | `SceneMarker` | ฐานรากของ 3 ฟีเจอร์ และเป็นสิ่งที่คู่แข่งไม่มี |
| 3 | **C — Discovery** | `Mood`, `MovieMood` | ตัวกรองเต็มรูปแบบ (เวลา + อารมณ์) ต้องรอ B3 เสร็จก่อน |
| 4 | **D — Passport** | (เฟส 2) | ต้องรอข้อมูลการดูจริงสะสม |

A กับ B ทำขนานกันได้ ไม่แตะไฟล์เดียวกัน (A อยู่ฝั่ง client ล้วน)
C ต้องรอ B3 เพราะใช้ sheet ตัวกรองเดียวกัน

## สิ่งที่ตัดออกโดยตั้งใจ (YAGNI)

| ตัดอะไร | เพราะอะไร |
|---|---|
| Auto-detect intro/credits ด้วย ML | เฟสแรกใส่มือพอ ระบบต้องทำงานได้เมื่อไม่มี marker อยู่แล้ว |
| จำ "ฉากที่เคยดู" รายช่วง | ต้องเก็บ coverage เป็น interval ต่อผู้ใช้ ใหญ่เกินคุณค่า ใช้ resume แทน |
| Mood ที่ผู้ใช้ติดแท็กเอง | ต้องมี moderation ก่อน ยังไม่มี |
| ระบบให้คะแนน 1–10 | เป็นฟีเจอร์ของตัวเอง ไม่ควรแอบเข้ามาทาง Passport |
| แชร์ Passport ออกโซเชียล | รอให้ Passport มีค่าพอจะแชร์ก่อน |

## คำถามที่ยังเปิดอยู่ (ต้องตอบก่อนเขียน implementation plan)

1. **ตัวกรองเวลา กรองที่ระดับตอน ตามที่เสนอใน B3 ใช่ไหม** — ถ้าเลือกระดับเรื่อง
   ซีรีส์จะหายไปจากตัวกรองทั้งหมด และ endpoint จะกลายเป็น `@Public()` ที่แคชได้
   (ถูกกว่ามาก แต่ผลลัพธ์แย่กว่าชัดเจน)
2. **ใครจะใส่ `SceneMarker` ให้คอนเทนต์จริง** — ถ้ายังไม่มีคน Part B จะออกมาเป็น
   ฟีเจอร์ที่ถูกต้องแต่ไม่มีข้อมูลป้อน
3. **ใครจะติดแท็ก mood** — เงื่อนไขเดียวกับข้อ 2 และเป็นตัวชี้ขาดว่าจะทำ C1 ไหม
4. **Sleep Mode ค่าเริ่มต้นควรเสนอเองไหมเมื่อเลยเที่ยงคืน** — เสนอเอง = แก้โจทย์
   ตรงจุดกว่า แต่เสี่ยงกวนใจ ข้อเสนอในเอกสารนี้คือเสนอครั้งเดียวตลอดกาล

## ภาคผนวก: เอกสาร ToS/Privacy

เอกสาร "นโยบายและข้อกำหนดการใช้งาน" ที่แนบมาพร้อมโจทย์ **ไม่ใช่ส่วนหนึ่งของ
สเปคนี้** เป็นงานคนละก้อน: หน้า static + จุดกด "ยอมรับ" ตอนสมัคร + การบันทึกว่า
ผู้ใช้ยอมรับเวอร์ชันไหนเมื่อไหร่ (ซึ่งต้องมี field ใหม่บน `User`)

จุดที่ต้องตรวจก่อนเอาขึ้นจริง: อีเมลในเอกสารสะกดว่า `support@ficler.com`
แต่เว็บไซต์สะกดว่า `www.flicer.com` — ตัวหนึ่งพิมพ์ผิด และช่องว่าง
`[ชื่อบริษัท]` / `[ที่อยู่บริษัท]` ยังไม่ได้เติม
